# 工单委派（workorder）

## 判定：按顺序问，命中即停

| # | 问题 | 是 | 否 |
|---|---|---|---|
| 1 | 有能跑通的验收命令吗？ | **委派** | 进 2 |
| 2 | 能拆出可机器验证的部分吗（纯逻辑 / 状态机 / 数据转换 / 解析）？ | **拆出来委派那部分，其余自己做** | 进 3 |
| 3 | 是「改一个文件 **而且** 改动 < 20 行」吗？ | 自己做 | 进 4 |
| 4 | 还在探索、不跑起来就不知道要做什么？ | 自己做 | **委派** |

第 4 条是唯一的主观例外。用之前先问自己：是真的说不清要做什么，还是没想清楚、或者没问用户？没问就先问，别拿"探索"当挡箭牌。

**新建文件不算小改动。** 从零写一个 ≥ 50 行的文件，走委派。

## 以下说法不算理由

这些实测被拿来绕过判定，逐条禁掉：

- ❌ "没有现成测试" —— 写测试正是 planner 的活
- ❌ "写规格等于做完了" —— 规格正是该委派出去的部分
- ❌ "单文件" —— 看行数，不看文件数。300 行的新文件不是小改动
- ❌ "我得逐行审查" —— 审查是验收步骤，不是跳过的理由
- ❌ "验收测不出手感" —— 手感测不出，逻辑测得出。拆开，别整体跳过
- ❌ "涉及渲染/交互所以没法测" —— 状态机可以测，先测状态机
- ❌ "跨模块" —— 除非真的十几个模块，否则不算

## 强制义务

任务超过 50 行、或要新建文件时，**回复的第一行**必须写判定结论：

```
委派：<一句话任务卡摘要>
```

或

```
未委派：命中例外 3a（改一个文件，12 行）
```

没写这一行，等于没做判定。用户看到"未委派"时可以当场驳回。

## 流程

```
planner（强模型，一次调用）    → 任务卡 JSON
executor（便宜模型，多轮迭代）  → 只拿到任务卡，看不到之前的对话和推理
验收（你自己，确定性命令）      → 跑测试 + 看 diff
```

executor 看不到 planner 想过什么，也看不到用户说过什么。**这是特性不是缺陷**——它省的就是这部分上下文。代价是任务卡必须自包含。

## 任务卡

固定五个字段：

| 字段 | 要求 |
|---|---|
| `goal` | 一句话说清达成什么 |
| `files` | 精确到文件，不要给目录 |
| `constraints` | 不能违反的硬规则（含"不许改 tests/"） |
| `acceptance_cmds` | 可直接执行的命令 |
| `out_of_scope` | 明确不做什么，至少三条 |

写卡的几条硬规矩：

1. **`acceptance_cmds` 必须是你确认过能跑的命令。** 实测踩过：planner 会写出 `python -m unittest discover -s tests -t . -v` 这种因为缺 `__init__.py` 直接 ImportError 的参数组合。要么先用 `--help` 或试跑确认，要么直接把项目里已经在用的那条命令抄过来。
2. **`out_of_scope` 不是形式主义。** 便宜模型会"超额完成"——顺手补 docstring、加类型标注、重构相邻函数。这些改动不在验收范围里，但会污染 diff、增加 review 成本。把不想要的显式写出来。
3. **只依据测试已定义的行为。** 测试就是契约。不要发明新接口，不要扩展语义。
4. **别把整个仓库路径丢给它。** `files` 越精确，executor 的搜索成本和跑偏概率越低。

## 模型选型

具体型号取决于你的 profile 配了哪些 provider，原则只有两条：

| 角色 | 选什么 | 为什么 |
|---|---|---|
| planner | **能读懂代码、指令遵循好**的那一档 | 每个任务只调一次，贵一点无所谓；但它写歪了全盘皆输 |
| executor | **额度大、单价低、上下文够长** | 全部上下文和多轮迭代都在它身上，是成本主体 |

判断方法：看你的 provider 里“每月能跑多少次”。executor 那一栏的数字要显著大于 planner——**瓶颈永远在 executor**。

另外别只看单价：便宜但返工率高的模型，实际成本可能更高。同一个任务跑三轮不如跑一轮。

设置页的下拉里，支持读图的模型前面有 👁。纯文本任务别选它们，白花钱。

## 图片 / 视觉任务

涉及 UI、截图、视觉比对时，三件事：

1. **选带 👁 的模型**——`input` 里声明了 `image` 的那些。设置页的模型下拉前缀 👁 就是标记。
2. **把图片路径写进任务卡**。executor 看不到你的对话，也不会自己去翻目录找图。支持读图但卡里没给路径，等于没有这个能力。
3. **在 `constraints` 里写清“只按截图里的布局改”**，否则它会自由发挥。

任务卡里给路径的写法：

```yaml
context:
  reference_images:
    - C:\proj\design\mockup.png
```

反过来，纯文本任务（重构逻辑、修测试）别选带 👁 的贵模型，白花钱。

## 验收（这一步不能省）

`report.tests_passed: true` 是**模型自述，不是证据**。必须：

1. 自己跑一遍 `acceptance_cmds`，看到真实退出码
2. `git diff` 看改动面是否符合 `files` 的预期
3. 确认 `tests/` 零改动（`git diff --stat -- tests/` 为空）
4. 检查有没有新增文件、新依赖

四条都过才算完成。

## 失败怎么处理

- **同一张卡重试**：把失败日志的**尾部**（最后 2000–3000 字符 + 第一个报错行号）回灌给 executor，不要回灌全文
- **连续 3 轮不过**：判定是任务卡有问题，退回 planner 重拆，而不是继续烧便宜模型的 token
- **executor 报"卡住了"**：先看它的 `notes`，通常是任务卡歧义或验收命令本身有问题

## 参考实现

本技能目录下的 `workflow.js` 是一个可直接跑通的 DSH workflow 脚本：planner 用 `schema` 约束输出任务卡，executor 用 `schema` 回报改动。改三个常量（`REPO` / `PLANNER` / `WORKER`）即可复用。

## 一句话总结

**强模型只做两件高价值的事：写清楚要什么，判断有没有做到。中间的活儿全部外包。**
